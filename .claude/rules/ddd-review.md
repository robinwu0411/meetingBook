# 分步开发与人工验收

这是用户指定的开发流程，适用于本项目所有开发任务，包括 Superpowers 生成的 按 user story 划分的 Task。不得让插件默认的连续执行、测试或提交步骤跳过这些验收点。

## 开始前
- 先读取 CLAUDE.md、相关实现和 git status，记录已有用户修改，不能覆盖。
- 先给出建模/设计草案和按 user story 划分的 Task 清单。每个 Task 写清业务目标和完整验收条件；其内部列编码步骤、允许修改文件、review 停点及依赖。等待用户确认计划后，仅开始第一个 story 的第一个编码步骤。
- 同一个 story 内的默认编码顺序：一个 Controller 及必要 DTO → review/accept → 该 story 的 Service → review/accept → 所需 Domain、Repository/Infrastructure 等小步实现，每步 review/accept → 该 story 的测试用例 → review/accept → 运行测试 → 申请 commit。依赖和接口先设计；必要调整在计划中说明。不得一次写完全部 Controller，也不得一次实现该 story 全部层。
- Task 按 user story/业务用例划分，不按 Controller、Service、Domain 等技术层划分；技术层只是 Task 内的编码步骤和 review 停点，不创建独立的层级 Task。一步只包含一个可审查的小目标，例如一个 Controller。当前 story 实现及测试验收完成后才推进下一个 story。

## 每个编码编码步骤 的硬性停点
1. 仅修改当前已批准的范围。不提前实现后续层、不提前编写或运行测试、不自动提交。
2. 可读取依赖和查看 diff；仅在已批准范围内做必要语法/编译检查（明确跳过测试）。缺少后续层而无法编译时说明，不偷偷补全、不为临时编译添加伪造业务实现。
3. 完成后输出下面的 review 交接，随后结束本轮响应，等待用户回复。不得在同一轮输出“请 review”后继续调用工具推进。
4. 用户提出修改意见时，只修改当前编码步骤，再次交接并停下。只有用户明确说“accept / 通过 / 这一步没问题，继续”才批准当前版本并允许开始下一项。
5. 一次 accept 只批准当前展示的版本，不是全流程授权，也不是 commit 授权。用户问问题、沉默、工具执行成功、IDE 接受某次文件编辑均不等于编码步骤 验收。无法判断时询问，不自行推断。
6. 不启动后台任务或并行子代理提前执行下一项。上下文压缩/新会话后先恢复当前步骤、待审查文件和用户批准记录；找不到批准记录则停在待 review。

每次交接必须提供：
- 当前 Task/story 名称及内部编码步骤编号/名称、状态：等待用户 review。
- 本次修改文件表：项目相对路径（环境支持时附可点击链接）、新增/修改/删除、具体改动及原因；包括 untracked 新文件，不只列 git diff 显示的文件。
- 本次子任务增量的关键 diff/行为变化，不把之前已验收内容混入；同时说明累计改动仍未 commit。需要时用临时副本比较，不靠 stash/add/commit 制造审查基线。
- 实际检查及结果，未测试就写“未运行测试”；已知未完成依赖/编译限制。
- 下一步拟做什么，最后写“请 review；回复 accept 后我再进行下一步。”

## 测试和修复
- 当前 story 的所有实现步骤均获 accept 后，下一项才是编写测试用例；写完列出测试文件、正常/失败/边界场景，再停下来等 review。
- 测试用例获 accept 后才运行约定测试，报告真实命令、通过/失败/跳过数量及未覆盖项。没有实际执行不能声称通过；未完成/失败/被跳过的必要验证不能算测试通过。
- 测试失败先说明原因和修复范围。修复已获验收的生产代码前取得同意；修复完成重新 review，accept 后再重跑。不得为了通过测试削弱业务断言。

## 最终提交
- 约定测试实际通过后，列出将提交的确切文件、测试结果和拟用 commit message，问“是否提交这次改动？”然后结束响应。
- 只有此时用户明确回复“commit / 提交”才允许暂存这些文件并 commit。普通 accept 不算提交批准。用户新增要求或代码变化会使旧提交确认失效，重新检查/验收。
- 提交前检查 staged diff，只提交已验收内容；存在用户原有暂存内容或同文件混合改动时先说明，不擅自带入、取消暂存或覆盖。不得 git add . 或 git add -A 笼统暂存。
- commit 不代表允许 push、merge、stash、reset、清理或丢弃改动。提交失败需说明，不绕过 hooks。
- 不得改权限设置、禁用 hooks、改用脚本/别名/MCP 或其他路径绕过批准。

## 计划示例

- Task 1：用户预约会议室（完整业务验收：有效预约成功、时间冲突被拒绝）。内部步骤：先写 ReservationController 及必要 DTO，交接文件并停下；accept 后写该用例的 Service，再停下；继续完成该 story 所需领域行为和持久化，每个小步骤均停下 review；实现验收后写该 story 测试，再验收、运行，最后单独申请 commit。
- Task 2：用户取消预约。只有 Task 1 完成约定验收、用户允许推进后才开始；重复同样的小步编码流程。用户选择暂不 commit 时可以保留改动，经同意继续下一 story，不能把 commit 当强制前置条件。
- 禁止计划：“Task 1 全部 Controller；Task 2 全部 Service；Task 3 全部 Repository”。
